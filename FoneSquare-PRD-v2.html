时区设计原则

🕐
核心原则：服务端存储统一 UTC+8（与企业现有系统及历史数据对齐）；APP 端展示转换为用户设备本地时区；业务日切（每日限额重置等）按 UTC+8 计算，不因用户时区而变化。

一、存储层规范

规则说明
统一 UTC+8 存储所有时间戳字段（created_at、updated_at、paid_at 等）以 UTC+8 存入数据库，服务器及数据库连接会话 time_zone 设为 +08:00
纯日期字段例外证件有效期（id_expiry_date）、营业执照有效期等存为 DATE 类型，不带时区——这些是证件上的物理日期
API 返回格式所有接口时间字段统一 ISO 8601 格式并带偏移量：2026-04-07T14:30:00+08:00，前端据此做本地时区转换
登录附带设备时区前端登录时传入 device_timezone（IANA 格式，如 Asia/Manila），写入 user_session 表，用于推送静默计算和服务端按需转换

二、展示层规范

规则说明
APP 端按用户本地时区展示前端接收到 +08:00 时间戳后，转换为用户设备本地时区展示。菲律宾用户看到 Manila 时间，中东用户看到 Dubai 时间
后台管理端统一 UTC+8运营后台、内部管理系统统一展示 UTC+8，与数据库一致，无需转换
绝对时间 + 相对时间结合24h 内用相对时间（"3分钟前"、"2小时前"）；超过 24h 用绝对时间（按用户本地时区格式化）
日期格式跟随语言EN → Apr 7, 2026 2:30 PM；简体中文 → 2026-04-07 14:30；繁體中文 → 2026年04月07日 14:30
PDF / 发票 / 对账单统一使用 UTC+8 并标注 (UTC+8)，作为法律和财务凭证的确定时间基准
邮件通知邮件正文中的时间标注 (UTC+8)，因无法获取用户阅读时的设备时区

三、业务逻辑时区归属

场景计算时区展示时区说明
每日购买限额重置UTC+8 00:00用户本地时区业务日切在北京时间零点，全球用户同一时刻重置。接口返回 resets_at: "2026-04-08T00:00:00+08:00"，前端转为用户本地时间展示倒计时
限额耗用时机—订单创建时扣减额度（非支付时），订单取消后释放
限额超额拦截文案用户本地时区将 resets_at 转为用户本地时间展示，如菲律宾用户看到 "Resets at 12:00 AM"（= 北京时间 00:00）
支付倒计时（30分钟）无时区概念基于时间戳差值倒计时，与时区无关
KYC 证件有效期纯日期比较—到期日当天 23:59:59（UTC+8）后才算失效
季度风控轮询UTC+8—定时任务按北京时间调度（如每季度最后一天 02:00 执行）
订单时间线UTC+8 存储用户本地时区创建、支付、发货、完成——存储 UTC+8，展示转为用户本地时间
推送通知/提醒（本期暂无）用户设备时区—读取 device_timezone，避免在用户当地 22:00–08:00 推送非紧急通知

四、边界场景处理

场景处理策略
菲律宾用户（UTC+8，与北京同时区）时间展示与北京一致，限额日切时刻 = 当地零点，无感知差异
限额重置时刻在非中国时区用户的白天如 UTC+4 用户的限额重置时刻 = 当地 20:00。
买卖双方不同时区看同一订单各自看到自己时区的本地时间。PDF 发票/对账单统一 UTC+8 并标注，作为法律凭证
用户跨时区移动设备时区自动更新，展示跟随变化；业务逻辑不受影响（UTC+8 日切不变）
夏令时（DST）UTC+8 本身无夏令时；前端使用 IANA 时区库（如 Asia/Dubai）自动处理用户侧 DST 转换

⚠️
设计背景：用户可能通过不同登录方式（手机号、邮箱、WhatsApp）注册多个独立账号。在 KYC 身份认证阶段通过证件号（唯一身份标识）识别同一自然人的多账号情况并做出处理。
⚡ 核心思路
不做账号合并，不做数据迁移。检测到重复身份时，引导用户登录已认证的账号，在已认证账号上补全登录方式（如添加当前使用的邮箱/手机号），通过 OTP 二次验证确认身份后完成。当前未认证账号自动废弃（文案上使用"此账号将不再使用"等友好措辞）。
⚡ 触发条件

检测逻辑

匹配范围
仅匹配 KYC 状态为「已通过」的账号；「已拒绝」或「审核中」不参与匹配

📐 合并规则
主账号判定

数据迁移

登录方式保留

合并时网络中断服务端事务保证原子性；中断保持原状，下次提交 KYC 时重新触发

三、绑定规则

📐 绑定规则详情
本质定义
「引导登录已认证账号 + 补全登录方式」。检测重复后引导用户切换到已认证账号，同时将当前登录方式添加到已认证账号，不迁移任何业务数据
主账号判定
以最早完成 KYC 认证的账号为主账号（即已通过认证的那个账号）
二次验证
用户确认操作后，必须通过 OTP 验证主账号身份。向主账号的主要联系方式（手机号 / WhatsApp）发送验证码，验证通过后才执行登录方式补全。防止他人使用伪造 / 盗用证件关联到别人的已认证账号
补全操作
OTP 验证通过后，将当前账号的登录方式（如邮箱）添加到已认证账号的登录方式列表。无数据迁移
登录方式保留
补全后，已认证账号可使用任意已绑定方式（手机号 / 邮箱 / WhatsApp）登录
密码处理
各登录方式保留各自的密码。邮箱登录密码不变，手机号 / WhatsApp 的 OTP 方式不受影响
未认证账号处理
当前未认证账号标记为「不再使用」，保留 30 天审计记录后归档。该账号不可再登录、不可再注册。文案要求：面向用户使用"此账号将不再使用"而非"废弃/删除/停用"
登录态处理
不自动切换登录态。操作成功后，当前会话登出，用户需使用已绑定的任意登录方式重新登录主账号。原因：直接切换登录态存在安全风险（若证件被盗用，攻击者会直接进入受害者的已认证账号）
🔒 安全设计：为什么需要 OTP 验证
攻击场景：攻击者获取他人证件副本 → 用邮箱注册新账号 → 提交 KYC 时证件匹配到受害者已认证账号 → 若无验证直接绑定，攻击者的邮箱会被绑定到受害者账号，获得其访问权限。
防御措施：要求用户提供主账号的 OTP，证明确实拥有该账号的控制权后才执行绑定。
✅ 与方案A（账号合并）的关键区别
不迁移任何业务数据。方案A 需要迁移 KYC 记录、订单数据、登录方式等，涉及多表事务；方案C 仅更新一个字段 login_method.user_id。原未认证账号直接停用，不存在数据归拢问题。本质是「登录方式搬家」，不是「两个家合并」。

🔧 关键技术点
OTP 发送
复用现有 SMS/WhatsApp OTP 通道。发送目标：主账号的主要联系方式。优先级：手机号 SMS > WhatsApp > 邮箱。有效期 5 分钟，6 位数字
OTP 验证
最多5次尝试，失败后锁定1小时。验证通过后立即使该 OTP 失效。需记录验证日志用于风控审计
DB 操作
UPDATE login_method SET user_id = :master_uid WHERE id = :current_login_method_id
单条 SQL，事务简单
账号停用
UPDATE user SET status = 'deactivated', deactivated_at = NOW(), deactivated_reason = 'duplicate_identity_bind' WHERE id = :current_uid
会话处理
不签发主账号 Token。绑定成功后，后端作废当前 Token（加入黑名单 / 标记过期），前端清除本地存储并跳转登录页。用户需重新登录，后端为主账号签发全新 Token
事务范围
OTP 验证通过后：login_method 更新 + user 停用 + Token 作废 + 绑定日志写入，四步在同一事务内完成
防重放
绑定接口需幂等设计：同一 current_uid + master_uid 组合仅允许执行一次，重复请求返回已完成状态
V2+ 扩展
若后续版本中未认证账号可能产生业务数据，需增加数据迁移逻辑和二次确认。V1.0 阶段不需要

一、系统架构总览

🔑
登录方式：使用OB账号体系登录管理后台（已有账号体系，无需新建）。登录后系统根据账号角色自动加载对应数据范围：管理员可查看全量商家数据；维护人仅可查看自己绑定的商家数据。

权限设计：功能权限 + 数据权限分离

🔐
设计原则：管理后台权限分为两个独立维度，互相正交、组合生效。
▸ 功能权限：控制账号可以执行操作（添加 / 编辑 / 停用 / 导出 / 配置限额 / 分配销售 / …），由 OB 账号权限点配置，可灵活组合分发到任意账号。
▸ 数据权限：仅控制账号可见的数据范围 —— 是看全量海外商家数据，还是只能看自己维护（绑定）的商家信息。它只决定"能看什么"，不决定"能不能做"。
▸ 实际能否操作 = 拥有该功能权限 ∧ 该商家落在数据权限范围内。

② 数据权限（仅控制可见数据范围）
数据权限值适用账号可见数据范围
全量海外数据管理员、运营、产品等可见所有海外商家、所有销售绑定关系、所有操作日志（不区分归属销售）
仅自己维护的商家销售/维护人仅可见自己绑定的商家（含自己添加自动绑定的）及该范围内的销售绑定历史；列表页隐藏"绑定销售"筛选；其他销售或"未分配"商家完全不可见
⚠️
数据权限的边界：
• 数据权限仅决定"能看到哪些商家"，与功能权限完全独立。如果一名销售被授予「编辑商家信息」功能权限，他依然只能编辑自己绑定的商家（数据权限收敛了写操作的对象）。
• 销售添加商家自动绑定 → 该商家立即落入"自己维护的商家"范围；如管理员后续将该商家更换给其他销售，原销售即刻失去对其的可见性。
• "未分配"商家（管理员添加未指定销售）只对"全量海外数据"权限可见。

四、对外查询接口

海外商家管理后台需要对外提供商家信息查询能力，供国内订单/风控/支付等系统调用。本接口部署在海外服务，需认证鉴权和访问审计。

接口概述
用途
国内系统通过此接口获取海外商家基本信息，用于订单创建、风控校验等场景
部署位置
海外服务器
认证方式
内部服务间鉴权（Token / 签名验证），不对外公开
访问审计
所有查询请求记录调用方、时间、查询条件，用于合规审计

查询方式

查询条件匹配方式返回字段说明
商家ID精确匹配商家名称、类型、状态、联系方式、所在地区最常用场景：业务系统通过商家ID查询商家信息
商家名称模糊匹配同上，支持分页返回运营查询场景，按名称关键词搜索
手机号精确匹配同上风控/客服场景，通过手机号定位商家
ℹ️
数据脱敏规则：接口返回的手机号、邮箱默认脱敏（如 +852 9***4567），仅特定权限的调用方可获取完整信息。证件号码、KYC照片等敏感信息不通过此接口返回。

🔌
架构说明（V2.5 调整）：
▸ 海外为商家数据的唯一数据源（Single Source of Truth），国内不再做镜像存储，也不再有双ID映射。
▸ 国内业务系统（订单/风控/支付）需要商家基本信息时，通过本对外查询接口按需调用，使用统一的 merchant_id。
▸ 敏感信息（证件号、KYC 照片）不通过此接口返回。

一、详情页结构与 Tab 设计

详情页采用「头部信息卡 + 5 个 Tab」结构。头部展示商家关键标识（名称、ID、类型、状态、维护人、注册日期）；Tab 内容按业务域分组（基本信息 / KYC 认证材料 / 限额与保证金 / 维护人绑定 / 操作日志）。

区域展示内容权限说明
头部信息卡商家名称、ID、类型 Tag（买家/卖家）、状态 Tag（使用/停用）、认证状态 Tag（未认证/已认证/账号受限）维护人、注册日期；所有可见角色均展示
头部右侧操作停用 / 启用需对应功能权限点
Tab 1 — 基本信息个人信息（姓名、手机号、邮箱、WhatsApp、地区、备注）— 选填查看通用；编辑需「编辑商家信息」功能权限
Tab 2 — KYC 认证材料证件类型 / 号码 / 姓名（脱敏）/ 有效期 / 证件照片（正面 / 背面 / 护照只一面）+ 选填内容：企业名称、证照类型、证照编号、法定代表/董事、企业地址、证照有效期、证照照片查看通用；证件号默认脱敏，原值需特定权限点击查看
Tab 3 — 限额与保证金（仅买家）香港店每日下单限额（店铺币种）输入框 + 保证金金额（店铺币种）输入框 + 保证金转账凭证图片上传；展示状态 / 确认时间 / 确认人查看通用；编辑需「配置限额 / 保证金」功能权限点（沿用既有权限）
Tab 4 — 维护人绑定当前绑定维护人（姓名、OB 账号、绑定时间、操作人）+ 绑定/解绑/更换 操作 + 历史绑定列表查看通用；写操作需「分配 / 更换 / 解绑销售」功能权限
Tab 5 — 操作日志时间线展示创建、KYC 审核、限额修改、销售绑定变更、停用/启用 等所有操作；含操作人、操作时间、变更前后值，信息脱敏数据权限按角色裁剪（销售仅看自己范围）

二、销售绑定（OB 账号）与数据权限

🔗
功能定位：管理员可为每个商家分配绑定对应的销售 OB 账号（归属 OB 账号体系）。绑定关系决定销售角色的数据权限范围 —— 销售仅可查看自己绑定的商家数据，实现数据隔离。
注意：绑定关系只影响"数据权限"维度（看哪些商家），不影响"功能权限"（能做哪些操作）。

绑定操作规则

操作说明所需功能权限
绑定销售在商家详情「销售绑定」Tab，从 OB 账号列表中选择销售进行绑定。一个商家同一时间仅绑定一个销售。分配 / 更换 / 解绑销售
更换销售解除当前绑定并重新选择新销售绑定。更换后原销售立即失去该商家的数据可见权限。分配 / 更换 / 解绑销售

查看绑定查看当前商家绑定的销售信息（姓名、OB账号、绑定时间、操作人）及历史。查看商家详情

详细业务规则

绑定规则
关系类型

三、限额与保证金（仅买家）

本 Tab 用于为买家类型商家配置香港店每日下单限额和管理保证金。卖家类型商家不展示此 Tab。

3.1 功能概述

功能项说明
每日下单限额配置以店铺币种（HKD）为单位设置买家单日累计下单金额上限，限额仅限制订单商品金额，不含服务费。
保证金管理买家通过线下转账方式缴纳保证金，运营在后台录入保证金金额并上传转账凭证图片，经运营确认后保证金生效。
修改记录每次限额或保证金变更均记录操作人、修改前后值、修改时间，展示在 Tab 5 操作日志中。

3.2 页面交互说明

交互元素交互行为
每日下单限额输入框可编辑输入框，单位 HKD。系统提供默认最小值；上限 = 保证金金额 × 10。输入时实时校验范围。
保证金金额输入框可编辑输入框，单位 HKD。填写买家实际转账的保证金金额。
保证金转账凭证上传图片上传区域，支持 JPG / PNG，单张 ≤ 5MB。上传后展示缩略图，可预览。
保证金状态展示当前保证金状态：未提交 / 待确认 / 已确认。
确认时间 / 确认人保证金确认后展示确认操作的时间和操作人。
「校验并保存」按钮点击后校验：① 限额 ≥ 默认最小值；② 限额 ≤ 保证金 × 10；③ 保证金变更时需上传凭证。校验通过后提交保存，校验失败展示红色提示信息。

3.3 限额配置业务规则

📌
核心规则：
• 限额上限 = 保证金金额 × 10（例：保证金 5,000 HKD → 限额上限 50,000 HKD）
• 未提交保证金 → 限额仅可配置为系统默认最小值，不可调高
• 保证金已确认 → 限额可在「默认最小值 ~ 保证金 × 10」范围内自由配置
• 保证金变更 → 若新上限 < 当前限额，系统提示运营先调低限额再变更保证金
• 限额仅限制订单商品金额，不含服务费
• 每次修改自动记录操作人、修改前后值、修改时间（写入操作日志）

3.4 权限要求

操作所需功能权限
查看限额与保证金查看商家详情（通用）
编辑限额 / 保证金「配置限额 / 保证金」功能权限点（沿用既有权限体系）

四、维护人绑定

本 Tab 用于管理商家与维护人（销售）的绑定关系。维护人绑定决定销售角色的数据权限范围——销售仅可查看自己绑定的商家数据。

4.1 功能概述

功能项说明
当前绑定信息展示当前绑定维护人的姓名、OB 账号、绑定时间、操作人。未绑定时展示「未分配」。
绑定维护人为未分配的商家选择维护人（从 OB 销售账号列表选择）进行绑定。
更换维护人解除当前绑定并重新选择新维护人。更换后原维护人立即失去该商家的数据可见权限。需填写变更原因。
解绑解除当前绑定关系，商家变为「未分配」状态。未分配的商家仅"全量海外数据"权限可见。
历史绑定记录表格展示该商家所有历史绑定记录：维护人姓名、OB 账号、绑定时间、解绑时间、操作人、变更原因。

4.2 页面交互说明

交互元素交互行为
当前维护人信息卡只读展示区：维护人姓名、OB 账号、绑定时间、操作人。未绑定时全部显示「—」。
「🔄 更换维护人」按钮点击展开更换面板（蓝色虚线边框）：① 下拉选择新维护人（从 OB 销售列表）；② 填写变更原因（必填）；③ 确认变更 / 取消。
「➕ 绑定」按钮仅当商家未绑定维护人时可操作。点击后展开绑定面板，选择维护人并确认。
「⛔ 解绑」按钮仅当商家已绑定维护人时可操作。点击后弹出确认提示，确认后解绑。
历史绑定记录表格表格列：维护人 / OB 账号 / 绑定时间 / 解绑时间 / 操作人 / 原因。按时间倒序排列。

4.3 业务规则

🔗
绑定规则：
• 一对多：一个维护人可绑定多个商家，一个商家同一时间仅绑定一个维护人
• 自动绑定：销售角色添加商家时，自动绑定到该销售名下
• 管理员添加：管理员添加的商家默认「未分配」，需在此 Tab 手动绑定
• 更换即时生效：更换维护人后，原维护人立即失去该商家的数据查看权限
• 变更原因必填：更换维护人操作必须填写变更原因，记录到操作日志
