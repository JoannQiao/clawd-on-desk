# 31-timezone — 时区处理规则

> **来源**：FoneSquare PRD v2 — 时区设计原则  
> **状态**：Draft  
> **最后更新**：2026-05-07

---

## 1. 核心原则

| 维度 | 规则 |
|---|---|
| **业务主时区** | `Asia/Hong_Kong` (UTC+8) |
| **服务端存储** | 统一 UTC+8，服务器及数据库连接会话 `time_zone` 设为 `+08:00` |
| **APP 端展示** | 按用户设备本地时区转换展示 |
| **Web 后台展示** | 统一 UTC+8，与数据库一致，无需转换 |
| **业务日切** | 按 UTC+8 计算（如每日限额重置），不因用户时区而变化 |

> **背景**：采用 UTC+8 存储（而非 UTC+Z）是为了与企业现有系统及历史数据对齐。

---

## 2. 存储层规范

### 2.1 时间戳字段

所有时间戳字段以 **UTC+8** 存入数据库。涉及时间的字段包括：

| 字段名 | 说明 | 存储类型 |
|---|---|---|
| `created_at` | 记录创建时间 | TIMESTAMP (UTC+8) |
| `updated_at` | 记录最后更新时间 | TIMESTAMP (UTC+8) |
| `last_login_at` | 用户最后登录时间 | TIMESTAMP (UTC+8) |
| `bound_at` | 维护人绑定时间 | TIMESTAMP (UTC+8) |
| `unbound_at` | 维护人解绑时间 | TIMESTAMP (UTC+8) |
| `confirmed_at` | 保证金确认时间 | TIMESTAMP (UTC+8) |
| `expires_at` | 到期时间（OTP / 导出文件等） | TIMESTAMP (UTC+8) |
| `paid_at` | 支付完成时间 | TIMESTAMP (UTC+8) |
| `audited_at` | KYC 审核通过时间 | TIMESTAMP (UTC+8) |
| `disabled_at` | 账号停用时间 | TIMESTAMP (UTC+8) |

### 2.2 纯日期字段（例外）

以下字段存为 `DATE` 类型，**不带时区**——这些是证件上的物理日期：

| 字段名 | 说明 |
|---|---|
| `id_expiry_date` | 证件有效期 |
| `business_license_expiry` | 营业执照有效期 |

> 到期判定：到期日当天 `23:59:59 (UTC+8)` 后才算失效。

---

## 3. API 返回格式

所有接口时间字段统一使用 **ISO 8601 格式并带偏移量**：

```
2026-04-07T14:30:00+08:00
```

前端据此做本地时区转换。

### 3.1 登录时附带设备时区

前端登录时传入 `device_timezone`（IANA 格式），写入 `user_session` 表：

```json
{
  "device_timezone": "Asia/Manila"
}
```

用于推送静默计算和服务端按需转换。

## 4. 展示层规范

### 4.1 APP 端

| 规则 | 说明 |
|---|---|
| **按用户本地时区展示** | 前端接收到 `+08:00` 时间戳后，转换为用户设备本地时区展示 |
| **相对时间** | 24h 内用相对时间（"3分钟前"、"2小时前"） |
| **绝对时间** | 超过 24h 用绝对时间（按用户本地时区 + locale 格式化） |

示例：

- 菲律宾用户 (UTC+8)：看到的时间与北京一致
- 迪拜用户 (UTC+4)：`2026-04-07T14:30:00+08:00` → 展示为 `10:30 AM` (Dubai 时间)

### 4.2 Web 后台

| 规则 | 说明 |
|---|---|
| **统一 UTC+8** | 运营后台、内部管理系统统一展示 UTC+8，与数据库一致 |
| **操作日志格式** | `YYYY-MM-DD HH:mm:ss` (HKT) |

### 4.3 日期格式跟随语言

| locale | 完整日期时间示例 |
|---|---|
| `en` | `Apr 7, 2026 2:30 PM` |
| `zh-Hans` | `2026-04-07 14:30` |
| `zh-Hant` | `2026年04月07日 14:30` |

### 4.4 PDF / 发票 / 对账单

统一使用 **UTC+8** 并标注 `(UTC+8)`，作为法律和财务凭证的确定时间基准。

### 4.5 邮件通知

邮件正文中的时间标注 `(UTC+8)`，因无法获取用户阅读时的设备时区。

## 5. 业务逻辑时区归属

| 场景 | 计算时区 | 展示时区 | 说明 |
|---|---|---|---|
| 每日购买限额重置 | UTC+8 00:00 | 用户本地时区 | 业务日切在北京时间零点，全球用户同一时刻重置。接口返回 `resets_at: "2026-04-08T00:00:00+08:00"`，前端转为用户本地时间展示倒计时 |
| 限额耗用时机 | — | — | 订单创建时扣减额度（非支付时），订单取消后释放 |
| 限额超额拦截文案 | 用户本地时区 | 用户本地时区 | 将 `resets_at` 转为用户本地时间展示 |
| 支付倒计时（30 分钟） | 无时区概念 | — | 基于时间戳差值倒计时，与时区无关 |
| KYC 证件有效期 | 纯日期比较 | — | 到期日当天 `23:59:59 (UTC+8)` 后才算失效 |
| 季度风控轮询 | UTC+8 | — | 定时任务按北京时间调度（如每季度最后一天 02:00 执行） |
| 订单时间线 | UTC+8 存储 | 用户本地时区 | 创建、支付、发货、完成——存储 UTC+8，展示转为用户本地时间 |
| 推送通知 / 提醒（本期暂无） | 用户设备时区 | — | 读取 `device_timezone`，避免在用户当地 22:00–08:00 推送非紧急通知 |

---

## 6. 特殊时效规则

| 场景 | 时效 | 计算方式 |
|---|---|---|
| OTP 有效期 | **5 分钟** | 服务端 UTC+8 时间戳比较 |
| OTP 重发间隔 | **60 秒** | 倒计时，无时区概念 |
| OTP 连续错误锁定 | **1 小时** | 连续 5 次错误后锁定 |
| 导出文件过期 | **7 天** | 从 `created_at` 算起，UTC+8 计算 |
| 支付倒计时 | **30 分钟** | 时间戳差值，无时区概念 |
| 每日限额重置 | **每日 00:00** | UTC+8 零点 |
| 已停用账号归档 | **30 天** | 从停用时间算起 |

## 7. 边界场景处理

| 场景 | 处理策略 |
|---|---|
| 菲律宾用户（UTC+8，与北京同时区） | 时间展示与北京一致，限额日切时刻 = 当地零点，无感知差异 |
| 限额重置时刻在非中国时区用户的白天 | 如 UTC+4 用户的限额重置时刻 = 当地 20:00 |
| 买卖双方不同时区看同一订单 | 各自看到自己时区的本地时间。PDF 发票 / 对账单统一 UTC+8 并标注，作为法律凭证 |
| 用户跨时区移动 | 设备时区自动更新，展示跟随变化；业务逻辑不受影响（UTC+8 日切不变） |
| 夏令时（DST） | UTC+8 本身无夏令时；前端使用 IANA 时区库（如 `Asia/Dubai`）自动处理用户侧 DST 转换 |

## 8. 前端实现建议

| 端 | 推荐方案 |
|---|---|
| APP（React Native） | `dayjs` + `dayjs/plugin/utc` + `dayjs/plugin/timezone`，或使用 `date-fns-tz` |
| Web 后台（React） | `dayjs` + timezone 插件，所有时间统一用 `Asia/Hong_Kong` 格式化 |
| 服务端 | 数据库会话 `SET time_zone = '+08:00'`；API 层输出 ISO 8601 带 `+08:00` 偏移量 |

## 9. 操作日志时间戳格式

Web 后台操作日志统一使用以下格式：

```
YYYY-MM-DD HH:mm:ss (HKT)
```

示例：`2026-04-07 14:30:25 (HKT)`

每次修改记录：操作人、修改前后值、修改时间。
