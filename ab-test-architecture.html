时序图 1：创建 & 启动实验

Sequence

运营人员通过配置后台创建实验，经就绪检查后启动的完整流程

sequenceDiagram
  autonumber
  actor OP as 运营人员
  participant WEB as 配置后台
  participant EXP as 实验管理服务
  participant DIM as 维度服务
(场次/品类)
  participant VAR as 变量服务
(质检报告/等级分)
  participant STAT as 统计引擎
  participant SPLIT as 分流引擎
  participant DB as 数据库

  OP->>WEB: 点击「创建实验」
  WEB->>DIM: 加载可用场次 & 品类
  DIM-->>WEB: 返回列表

  OP->>WEB: 填写假设 + 选择场次/品类
  WEB->>EXP: 检查冲突（同场次×品类是否有运行中实验）
  EXP->>DB: 查询活跃实验
  DB-->>EXP: 无冲突 ✓
  EXP-->>WEB: 可以创建

  OP->>WEB: 选择对照组/实验组方案
  WEB->>VAR: 加载可用方案版本
  VAR-->>WEB: 返回方案列表（V1/V2）

  OP->>WEB: 配置流量比例（对照70:实验30）
  OP->>WEB: 设置指标（主要/次要/护栏）

  OP->>WEB: 填入统计参数（基线率/MDE/日均流量）
  WEB->>STAT: 计算所需样本量 & 预估天数
  STAT-->>WEB: 每组 6,340 人 / 预计 9 天

  OP->>WEB: 点击「保存草稿」
  WEB->>EXP: 保存实验配置（状态=草稿）
  EXP->>DB: INSERT experiment
  DB-->>EXP: OK
  EXP-->>WEB: 保存成功

  rect rgb(240, 253, 244)
    Note over OP,DB: 🔍 就绪检查（Hard Gate）
    OP->>WEB: 点击「就绪检查 & 启动」
    WEB->>EXP: 执行就绪检查
    EXP->>EXP: ✓ 假设已锁定
    EXP->>EXP: ✓ 主要指标已冻结
    EXP->>EXP: ✓ 样本量已计算
    EXP->>EXP: ✓ 护栏已设置
    EXP-->>WEB: 检查通过（5/6 通过，1 项警告）
    WEB-->>OP: 展示检查结果弹窗
  end

  OP->>WEB: 确认启动
  WEB->>EXP: 启动实验（状态→运行中）
  EXP->>SPLIT: 注册分流规则（场次+品类+比例）
  SPLIT->>DB: 写入分流配置
  SPLIT-->>EXP: 分流就绪
  EXP->>DB: UPDATE status = RUNNING
  EXP-->>WEB: 🚀 实验已启动
  WEB-->>OP: 跳转实验详情页

时序图 2：买家访问 → 分流 → 展示

Sequence

买家浏览商品详情页时，分流引擎决定展示哪个版本的质检报告/等级分

sequenceDiagram
  autonumber
  actor BUYER as 买家
  participant APP as 商品详情页
(H5/App)
  participant GW as API Gateway
  participant SPLIT as 分流引擎
  participant CACHE as Redis 缓存
  participant GOODS as 商品服务
  participant REPORT as 质检报告服务
  participant TRACK as 埋点 SDK

  BUYER->>APP: 打开商品详情页
  APP->>GW: 请求商品数据
(user_id, goods_id, session_type, category)

  GW->>SPLIT: 查询用户分组
  SPLIT->>CACHE: 查找用户已有分组
  
  alt 用户已有分组
    CACHE-->>SPLIT: group = treatment
  else 新用户 — 首次进入
    SPLIT->>SPLIT: Hash(user_id + experiment_id) % 100
    Note right of SPLIT: hash=42, 阈值=70
42 < 70 → 对照组
    SPLIT->>CACHE: 写入 user_id → control
    CACHE-->>SPLIT: OK
  end

  SPLIT-->>GW: 返回分组 = control + 方案 = 质检报告V1

  GW->>GOODS: 获取商品基础信息
  GOODS-->>GW: 商品数据

  GW->>REPORT: 获取质检报告（version=V1）
  REPORT-->>GW: V1 质检报告数据

  GW-->>APP: 返回完整数据
(商品 + V1质检报告 + 分组标识)

  APP-->>BUYER: 渲染页面（展示 V1 质检报告）

  rect rgb(239, 246, 255)
    Note over BUYER,TRACK: 📊 行为追踪
    BUYER->>APP: 浏览 / 点击 / 出价
    APP->>TRACK: 上报事件
(experiment_id, group, action, timestamp)
    TRACK->>TRACK: 异步写入事件日志
  end
分流一致性保障：同一用户在实验周期内始终进入同一组（用户级哈希 + Redis 缓存双重保障）。仅当运营调整比例且该调整仅作用于新用户时，才可能出现分流变化。

时序图 3：动态调整流量比例

Sequence

运营将实验从 3:7 调整为 2:8（Dynamic Traffic Allocation），仅对新用户生效

sequenceDiagram
  autonumber
  actor OP as 运营人员
  participant WEB as 配置后台
  participant EXP as 实验管理服务
  participant SPLIT as 分流引擎
  participant CACHE as Redis 缓存
  participant STAT as 统计引擎
  participant DB as 数据库

  OP->>WEB: 点击「调整比例」
  WEB->>EXP: 获取当前实验状态
  EXP-->>WEB: 当前 对照70 : 实验30

  OP->>WEB: 调整为 对照80 : 实验20
  OP->>WEB: 填写调整原因

  WEB->>STAT: 计算影响
(新比例下需要多少额外天数?)
  STAT-->>WEB: 按 8:2 比例还需 ~12 天达到显著性

  WEB-->>OP: 展示统计影响提示
  OP->>WEB: 确认调整

  WEB->>EXP: 提交比例变更

  rect rgb(254, 243, 199)
    Note over EXP,CACHE: ⚡ 分流规则热更新
    EXP->>SPLIT: 更新分流阈值
(70→80)
    SPLIT->>CACHE: 更新全局分流配置
(不清除已有用户分组!)
    CACHE-->>SPLIT: OK
    SPLIT-->>EXP: 分流规则已生效
  end

  EXP->>DB: 记录 Phase 2 起始
(新比例 + 时间戳 + 原因)
  DB-->>EXP: OK

  EXP->>DB: 写入操作日志
  DB-->>EXP: OK

  EXP-->>WEB: 调整成功
  WEB-->>OP: ✅ 比例已更新为 8:2

  Note over SPLIT,CACHE: 后续新用户按 80:20 分配
已分组用户保持原组不变

  rect rgb(240, 253, 244)
    Note over STAT,DB: 📊 分阶段统计
    STAT->>DB: Phase 1 数据（7:3 阶段）独立统计
    STAT->>DB: Phase 2 数据（8:2 阶段）独立统计
    STAT->>STAT: 合并分析需考虑 Phase 权重
  end
关键设计约束：调整比例时绝不清除已有用户的分组缓存。已进入对照组的用户始终留在对照组，已进入实验组的用户始终留在实验组。新阈值仅影响后续首次进入实验的新用户。这是保证实验有效性的核心原则。

时序图 4：实验结果分析 & 决策

Sequence

实验达到预计样本量后，统计引擎自动分析并辅助运营做出上线/拒绝决策

sequenceDiagram
  autonumber
  participant CRON as 定时任务
  participant STAT as 统计引擎
  participant LOG as 事件日志
(ClickHouse)
  participant EXP as 实验管理服务
  participant GUARD as 护栏监控
  participant DB as 数据库
  actor OP as 运营人员
  participant WEB as 配置后台

  rect rgb(239, 246, 255)
    Note over CRON,LOG: ⏰ 每日定时分析（如 02:00）
    CRON->>STAT: 触发实验数据分析
    STAT->>LOG: 查询实验期间事件数据
(按 experiment_id + group 聚合)
    LOG-->>STAT: 返回聚合指标
(对照/实验各自的转化数、样本数)
  end

  STAT->>STAT: 频率学派检验
(Z-test, p-value, CI)
  STAT->>STAT: SRM 检测
(实际比例 vs 预期比例)
  STAT->>STAT: 分人群切片分析

  alt 护栏触发
    STAT->>GUARD: 检查护栏指标
    GUARD->>GUARD: 退货率 +3.5% > 阈值 +2%
    GUARD->>EXP: 🚨 触发护栏告警!
    EXP->>EXP: 自动暂停实验
    EXP->>DB: 状态 → 已暂停
    EXP-->>OP: 推送告警通知
  else 护栏安全
    STAT->>GUARD: 检查护栏指标
    GUARD-->>STAT: 全部安全 ✅
  end

  STAT->>DB: 写入分析结果快照
  DB-->>STAT: OK

  alt 达到显著性
    STAT->>EXP: 通知实验达到统计显著
(p=0.003, 提升+18.3%)
    EXP->>DB: 状态 → 待决策
    EXP-->>OP: 推送通知：实验结果已出

    OP->>WEB: 查看实验结果
    WEB->>DB: 获取分析报告
    DB-->>WEB: 返回完整结果

    WEB-->>OP: 展示结果 + 建议

    alt 上线
      OP->>WEB: 决策 → 全量上线
      WEB->>EXP: 结束实验 + 记录决策
      EXP->>DB: 状态 → 已结束
决策 = 全量上线
      EXP-->>WEB: 实验归档完成
      Note right of OP: 通知商品服务
将实验组方案设为默认
    else 拒绝
      OP->>WEB: 决策 → 拒绝上线
      WEB->>EXP: 结束实验 + 记录学习点
      EXP->>DB: 状态 → 已结束
决策 = 拒绝
    end

  else 未达显著性
    STAT->>EXP: 样本量充足但未显著
(p=0.12)
    Note right of STAT: 建议：延长实验
或加大 MDE 预期
  end
决策原则：① 统计显著 + 护栏安全 → 建议上线 ② 统计显著但护栏触发 → 不可上线 ③ 未达显著 → 延长或结束并记录学习 ④ 所有决策必须记录原因，沉淀到知识库
